# 交互实现与参考边界

## 设计方向

产品是 Java 泛型与类型安全学习工作台，连接规则、作答、证据和可编辑学习成果。界面性格为安静、准确、可亲近；视觉场景为阅读桌面与代码实验台。知识规则、类型表达式与真实反馈承担视觉内容，不加入虚构数据装饰。主要辨识元素为 `<T>` 标识、G01–G16 概念编号、固定版本的来源摘要与青绿色动作。

v0.5 至 v0.6 的反馈参考 Apple Human Interface Guidelines 的 [Motion](https://developer.apple.com/design/human-interface-guidelines/motion) 与 [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback)：动态变化要说明操作结果、保持简短且可以中断，状态反馈出现在用户正在操作的位置。实际实现为 150ms 控件过渡、260ms 面板过渡和 80ms 按压反馈；减少动效时直接呈现状态。没有引入新的动效库或用动画计时推测任务完成。

## 有意义的动态关联

1. 阅读选择关联概念 → 真实题目作答 → 学习证据与复习计划。
2. 错误或受助作答 → 错题源稿 → 预测/证据回看/复练 → 新的真实 attempt，重复题族不刷独立样本。
3. 课程知识卡 → 文档/幻灯片引用 → 固定来源的源稿版本 → 后台静态导出与真实文件下载。
4. 目标、记忆和最近作答 → 固定上下文快照 → 本地证据工作流或导师请求 → 带来源的学习文档。
5. 目标更新、归档或记忆撤回 → 上下文/任务/作品来源失效 → UI 隐藏旧导师答案并禁止旧源复练、导出。
6. 第二编辑端保存新版本 → 事件轮询重新读取 → 当前脏稿保留 → 用户比较并明确选择后续版本基线。
7. 私有图片 → 验证上传与固定 ASSET 引用 → 幻灯片排版 → 带图片的真实 PPTX 文件；素材撤回后相关引用失效。
8. 历史错误或受助作答 → 明确选择 attemptIds → 同一组证据的快照与学习任务 → 新学习文稿、演示文稿或复练笔记。

| 页面与入口 | 实际交互 | 状态、容量与可达性 |

TYPE_FLOW 的读写方向与后端一致：源位置是容器，READ 的目标是接收类型，WRITE 的目标是待写入的值类型。代码修复对照分别记录原始源码和修改后源码的实际编译任务；普通逐层引导来自题目提示，不冒充未配置模型的分析。

页面样式使用同一套字号、表面、控件目标和短过渡。新增工作台在 320 / 390 像素采用纵向布局，内容编辑的六个步骤分为三列两行，当前步骤保持完整可见；长哈希和差异正文允许换行，原稿、差异及代码对照使用随主题变化的正文色。表格与图谱保留自己的滚动区域。实际视觉、键盘滚动和触控尺寸是否通过，以本次 Chromium 报告与新截图复核为准，代码中的媒体查询不代表设备验收。

首屏容量也属于交互成本：`App.tsx` 将作品、内容、学习创作、评测与运营页面分为按需模块，等待时使用稳定的页面加载状态。最终 `npm run build` 的主脚本为 354.39 kB／gzip 109.99 kB；同功能拆分前为 518.29 kB／gzip 154.75 kB，首屏 gzip 减少约 29%。作品、内容、评测、学习创作和运营页各自 gzip 为 20.74、14.97、9.28、5.65、2.83 kB。主 CSS gzip 为 15.27 kB。这里记录构建容量，不把它换算成未经测量的响应时间或设备性能。

## 三轮审查与证据

第一轮逐页核对请求契约、异步状态、草稿与能力：补齐账户/阅读/趋势、代码与提示、素材与 Office、学习任务和内容发布入口。第二轮针对真实风险复核并增加回归：重点修正保存基线、迟到请求、非重叠轮询、空分数判定、多来源修订和独立表单脏状态。第三轮使用真实后端与实际 React 页面贯通业务、下载并检查真实文件字节，同时运行类型、单元测试及生产构建。

v0.6 类型检查与 65 项组件测试已通过，实际结果以 `test-results/unit-report.json` 为准。新增用例针对真实风险：并发修订与独立草稿、证据读取失败、取消中的空指标、变式提示和输入恢复、历史区块许可、写入方向、原稿／修订稿的独立编译结果、运营权限与无样本数据，以及实际 HTML 输入规则和跨账户私有定位。前轮截图修复后的干净 v0.6 JAR 已完成全部 24 条真实 HTTP DOM 链路；本次原生输入与身份边界修复后的新包仍需重新绑定运行。链路和 jar 哈希分别写入 `test-results/live-dom-report.json` 与 `test-results/dom-runtime-report.json`，各次结果只对应其实际输入。测试仅适配 Node cookie、DOM 文件到真实 multipart 的传输、jsdom 缺少的视口 API，以及逐字节确认文件后仍误报空文件的 jsdom 原生校验差异；没有伪造业务响应，Chromium 保留原生校验。三轮代码及联调审查不等同于图形浏览器或屏幕阅读器通过。

第四轮直接核对首次 v0.6 Chromium 的真实失败与截图：前 13 个场景通过，第 14 个因审核详情未返回就计算折叠面板数量而失败；检查页面与控制台未出现异常。将等待条件改为实际可见或已移除后再执行原有唯一性／缺失断言，保持业务断言和失败退出。原稿文字对比不足与手机步骤遮挡来自实际截图，分别用随主题变化的正文色和两行步骤布局修复。后续截图逐次记录渲染主题、正文对比度与当前步骤可见性，并覆盖真实保存的深色偏好和系统深色变化；完整图形结果仍由新 CI 产物与人工复核决定。

第五轮核对第二次 Chromium：20 个业务场景通过、59 张实际截图完成，但最终零控制台错误门禁拒绝了无效的课程版本号输入规则及跨账户残留私有评测地址的 404。前者修正 HTML Unicode sets 模式下的字面短横线写法，后者在明确退出、运行中失效或启动检查确认 401 时清理旧定位，初始已认证会话仍能正常打开自己的深链接。组件与真实驱动都增加针对性的正反输入及身份边界回归；没有添加任何 404 忽略规则，新包和新 CI 必须重新验收。

## 尚待专门验收的部分

本地环境禁止 Chromium 所需的内部 socket，因而本地不提供伪造截图或“已视觉验收”的结论。真实浏览器脚本已准备，移动视口、触屏目标、完整焦点流、深浅主题视觉和原生下载以 CI 的浏览器产物为准。屏幕阅读器与不同移动输入法仍需要具体设备验证；不把 DOM 渲染或代码中的媒体查询等同于已在设备上验证。
